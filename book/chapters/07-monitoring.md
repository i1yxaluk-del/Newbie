# Prometheus, Grafana и доставка оповещений

## От числа к действию

Prometheus хранит временные ряды: значение, время и метки объекта. Exporter выдаёт показатели ОС/приложения, Prometheus опрашивает его. Правило задаёт условие сбоя; Alertmanager группирует похожие сигналы и выбирает получателя. Grafana показывает запросы, но не является первичным источником фактов.

Например, «backup_success=1» означает успех последнего наблюдавшегося задания, а не наличие пригодной сегодняшней копии. Для календаря нужны ещё время самого запуска и свежесть обработчика. Иначе вчерашнее зелёное значение повторяется сегодня. В текущем Backups календарь встроен в прежний dashboard, а не создан как отдельная рабочая витрина.

## Несколько способов доставки

Backend MAX Bot API получает лиды через бота, MAX alerter отправляет monitoring через пользовательскую pymax-сессию. У них разные secrets и жизненный цикл. Файл `/session/max.db` соответствует действующему входу пользователя; авторизацию с SMS выполняет оператор через `auth --authorize`, не автоматический цикл.

Matrix alerter отправляет в комнаты Matrix; email — другой канал. Несколько каналов на одной VM не независимы при отказе host. `/health` может проверять только наличие настроек: нужно реальное тестовое сообщение и подтверждение согласованным получателем.

## Почему сохранённый dashboard может не работать

Правильный запрос к индексу не доказывает отрисовку. Учебные Wazuh-карточки уже ломались из-за отсутствующего `fontSize`, хотя API сохранял их и данные существовали. Теперь проверяются правила, индекс, запросы **и авторизованный браузер**. Приёмка по одному зелёному тесту пропускает целый слой.

## Практика и результат

Выбрать одну метрику и показать её target, запрос, правило, получателя, человека и время начала диагностики. Затем найти различие между «нет данных», «ошибка», «устарело» и «успешно». Маркетолог не переводит «зелёный dashboard» в «гарантированный uptime». Уроки: [Prometheus/Grafana](../VIDEO_GUIDE.md#мониторинг-автоматизация-и-безопасность).
