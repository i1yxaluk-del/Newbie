# Стандарт учебника MSPShield Academy

Версия проекта, относительно которой строится программа: `main` → `89249e43a4e8b2e90d562307ef244ba95288c64c` от 28.09.2026.

## Почему предыдущая версия не подходит

Предыдущий текст увеличивал объём повторением одинаковых рамок: «вход — состояние — выход», «evidence over confidence», одинаковых вопросов и общих предостережений. Это создаёт иллюзию глубины, но не формирует рабочую модель. Определение вроде «container — изолированная среда» бесполезно, пока не объяснено: что именно изолируется, какие Linux-механизмы это делают, что остаётся общим с host, где лежат данные и почему container исчезает после recreate, а volume — нет.

В новой книге запрещены главы-словари и одинаковые секции ради шаблона. Термин вводится непосредственно перед первым применением, связывается с уже известным понятием и сразу проверяется на реальном примере.

## Для кого написана книга

Читатель умеет войти по SSH, выполнить знакомую Linux-команду, видел YAML и Docker, но пока не может:

- предсказать результат незнакомой команды;
- объяснить сеть Docker и путь HTTP-запроса;
- самостоятельно спроектировать backup/restore;
- отличить метрику от alert и SLA;
- рассчитать цену услуги через труд, риск и capacity;
- превратить лид в управляемый клиентский lifecycle.

Книга должна довести читателя до уровня Owner, который понимает систему, может собрать аналог с нуля, изменить архитектуру осознанно и знает, когда нужен профильный специалист.

## Методика обучения

### 1. От существующей схемы к деталям

Сначала читатель видит целую систему на одной странице: пользователь → DNS → Caddy → backend → MongoDB и Prometheus → Alertmanager → MAX/email. Затем схема разбирается по слоям. Это advanced organizer: новое знание получает место в общей модели, а не висит отдельным термином.

### 2. Worked example → completion task → самостоятельная работа

Новичку сначала показывается полностью разобранный пример. Затем часть шагов убирается, и читатель завершает решение. После этого задача выполняется с нуля. Подсказки постепенно исчезают — guidance fading. Такой порядок снижает лишнюю cognitive load и лучше готовит к переносу навыка, чем немедленная задача «разверни всё сам».

### 3. Один новый слой сложности за раз

В первом Linux-стенде нет Caddy, TLS, Prometheus и облака. В Docker-лаборатории сначала один stateless container, затем volume, сеть и только после этого Compose. В бизнес-блоке сначала стоимость одного часа и capacity, затем пакет, цена, воронка и договор. Нельзя одновременно учить синтаксис YAML, сеть, TLS и recovery.

### 4. Объяснение причин, а не ритуалов

Каждая команда разбирается только там, где нужна. Для неё объясняются: кто её исполняет; какие аргументы получает программа; что shell обрабатывает до запуска; какой объект изменяется; где увидеть результат; что команда не проверяет. Команда без модели состояния в книгу не попадает.

### 5. Retrieval practice и spacing

В конце главы нет длинного теста на узнавание. Есть 5–8 коротких вопросов из памяти и одна задача без подсказки. В начале следующей главы — возврат к двум старым понятиям. Через 3–4 главы навык повторяется в другом контексте: например, permissions сначала в Linux, затем в bind mount, затем в backup restore.

### 6. Interleaving после освоения базы

Похожие задачи перемешиваются только после отдельного изучения: network failure отличают от application failure, credential failure — от DNS, low margin — от cash-flow gap. Раннее перемешивание перегружает novice; позднее учит диагностике.

### 7. Безопасная работа с ошибками

Failure lab создаёт одну известную неисправность на локальной VM: неверный env, закрытый порт, отсутствующий volume, просроченный credential. Читатель сначала прогнозирует симптомы, затем диагностирует. На production такие эксперименты запрещены без change и rollback.

### 8. Mastery gates вместо «прочитал главу»

Переход определяется действием: читатель объясняет схему без текста, выполняет практикум, восстанавливает ошибку и отвечает на вопрос «почему». Время и число страниц не являются доказательством освоения.

## Формат настоящей главы

Названия разделов выбираются по содержанию, а не копируются из шаблона. Но логика главы сохраняется:

1. **Живая задача.** Конкретная ситуация Owner: например, после reboot MAX перестал отправлять alerts.
2. **Недостающая модель.** Объяснение только тех понятий, без которых ситуацию нельзя понять.
3. **Разобранный пример.** Реальный фрагмент MSPShield с пояснением каждой существенной строки.
4. **Что происходит во время выполнения.** Последовательность процессов, файлов, sockets, API и данных.
5. **Типичные ошибки.** Причина → наблюдаемый симптом → проверка → исправление.
6. **Практика с поддержкой.** Команды и checkpoints даны частично.
7. **Самостоятельная задача.** Аналогичная, но не идентичная ситуация.
8. **Связь с системой и бизнесом.** Только конкретные последствия: downtime, RTO, трудозатраты, SLA или риск.
9. **Короткое повторение из памяти.** Без переписывания определений.

Заголовка «Проверяемые результаты» не будет. Нужный итог занятия записывается одной естественной фразой во вводном абзаце и доказывается практикой.

## Как писать определения

Плохое: «Idempotency — свойство безопасного повтора».

Хорошее: «Операция идемпотентна, если повтор с тем же идентификатором не создаёт второй бизнес-результат. Если браузер дважды отправит форму с ключом `abc`, backend должен вернуть ссылку на уже созданную заявку, а не создать две карточки Kaiten. HTTP-запросов может быть два; заявка должна остаться одна».

Каждое определение обязано содержать:

- родовое понятие;
- отличие от соседнего понятия;
- конкретный пример;
- контрпример или границу применимости;
- место в MSPShield.

## Контроль галлюцинаций

Каждое утверждение при написании главы получает один из четырёх статусов:

- `REPO FACT` — подтверждено файлом в commit `89249e43` или более новом проверенном commit;
- `EXTERNAL FACT` — подтверждено первичной/официальной документацией с URL и датой доступа;
- `MODEL` — учебная модель или упрощение, явно названное моделью;
- `ASSUMPTION` — предположение для задачи; не выдаётся за состояние production.

Правила:

1. Версии, порты, пути, команды и цены берутся из текущего источника истины, а не из памяти модели.
2. Команда из runbook не объявляется безопасной, пока не разобраны prerequisites и side effects.
3. «Backup работает» нельзя писать без restore evidence; «RTO = N» — без измеренного упражнения.
4. Alert delivery через MAX нельзя называть официальным MAX Bot API: это `pymax userbot`, ручная авторизация и `/session/max.db`.
5. Юридическое объяснение отделяется от юридического заключения; последнее требует юриста РФ.
6. Экономическая цифра сопровождается формулой, исходными значениями, периодом и sensitivity check.
7. При конфликте документации глава останавливается и фиксирует discrepancy; автор не угадывает.

## Актуальные уроки production, обязательные для книги

- `maxapi-python` закреплён на 2.4.1 после `client.unsupported-version`.
- MAX-авторизация: SMS, при включённом 2FA — пароль; session хранится в bind mount и переживает reboot.
- До DNS switch проверяется TCP-доступность IP из целевого региона, а не только ICMP.
- Caddy после cloud-init может оставаться на заглушке 503; `MSP_DOMAIN` для systemd задаётся отдельно.
- Restore должен находить плоскую и вложенную раскладку; root-only glob нельзя бездумно использовать после `sudo`.
- Для Stalwart нужны оба тома; пустой data volume приводит к bootstrap mode.
- Postbox DKIM публикуется CNAME по значениям консоли; маршрут Stalwart может сохранить старые credentials и дать очередь с 535.
- При смене облачного аккаунта restic/S3 credentials пересоздаются.
- Публичный SSH закрывается только после проверки AWG и наличия аварийного пути возврата.
