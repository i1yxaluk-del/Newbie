# 2. Исследование незнакомой системы без угадывания

> **Учебная ситуация.** После инцидента документация и фактическая конфигурация расходятся. Нужно установить правду, ничего не ломая.

Предыдущая глава: [глава 1](./01-от-услуги-к-работающей-системе.md).

## Модель, которую нужно построить

Начинайте с наблюдения: версия, process, socket, config path, log и health. Гипотеза появляется после факта, а не вместо него.

README описывает намерение; исполняемый Compose, systemd unit и runtime inspect показывают реализацию. Источник может устареть, поэтому важна привязка к commit.

Незнание фиксируется явно. Надпись ASSUMPTION безопаснее уверенного вымысла, потому что её можно проверить.

## Термины в рабочем смысле

### evidence

Минимальный проверяемый артефакт: timestamp, exit code, hash, запрос/ответ, metric или подписанный документ. Скриншот зелёной панели без target и времени — слабое evidence.

### interface

Согласованная граница обмена между компонентами: адрес/протокол, формат, допустимые ошибки и ожидания по времени. `backend:8001` — сетевой интерфейс; Order Form — организационный интерфейс между продажей и эксплуатацией.

### state

Данные, от которых зависит следующий результат и которые переживают отдельную операцию: документ Mongo, файл session, volume, DNS-запись. Лог процесса не всегда является состоянием.

## Что происходит внутри

Работайте от дешёвых read-only наблюдений к более дорогим. Сначала версия и конфигурация, затем process/socket, затем локальный request, затем внешний request. Меняйте один фактор только после фиксации baseline. Так расследование остаётся воспроизводимым, а найденная корреляция не выдаётся за причину.

## Разобранный пример

```bash
git rev-parse HEAD
docker compose config --services
docker compose ps
ss -lntp
curl -fsS http://127.0.0.1:8001/api/health
```

### Как читать пример

- `git rev-parse HEAD` — Git-команда читает или изменяет working tree/index/refs; перед mutation сравните `status` и `diff`.
- `docker compose config --services` — Команда строит итоговую Compose-модель после interpolation и merge; она не запускает services.
- `docker compose ps` — Разделите строку на программу/оператор, options и operands; затем по документации установите side effect и exit semantics.
- `ss -lntp` — `ss -lntp` показывает listening TCP sockets, numeric addresses и process metadata при достаточных правах.
- `curl -fsS http://127.0.0.1:8001/api/health` — `curl` создаёт реальный HTTP/TLS request. `-f` делает HTTP 4xx/5xx ненулевым exit, `-sS` скрывает progress, но оставляет ошибки.

## Практикум

1. Соберите read-only inventory одного сервиса.
2. Сравните README, Compose и runtime.
3. Запишите три подтверждённых факта и одно расхождение.

## Если результат не совпал с ожиданием

| Наблюдение | Что это означает | Следующая проверка |
|---|---|---|
| `docker ps` пуст | Это сужает область поиска, но не доказывает единственную причину | возможно выбран другой context или нет прав к socket. |
| Health 200 не доказывает доступность зависимостей, если endpoint их не проверяет. | Это сужает область поиска, но не доказывает единственную причину | Проверьте связанные входы, состояние и журналы; не угадывайте причину. |

## Самостоятельная работа

Решите изменённый вариант исходной ситуации: **После инцидента документация и фактическая конфигурация расходятся. Нужно установить правду, ничего не ломая.** Измените один существенный параметр — host, port, credential, dataset, пакет или ограничение клиента — и сначала письменно предскажите результат. Затем выполните проверку на безопасном стенде. В отчёте оставьте исходное предположение, фактическое наблюдение, причину расхождения и способ восстановления.
