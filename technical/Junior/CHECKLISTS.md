## Приём нового клиента — Bronze

Длительность: 2–3 рабочих дня.

### День 0 — договор и реквизиты
- [ ] Подписан договор + приложения (SLA, поручение ПДн)
- [ ] Получены реквизиты клиента (для актов)
- [ ] Получен счёт, ждём оплату
- [ ] Заведена папка `/opt/mspshield/clients/<slug>/`
- [ ] Заведён Telegram-чат «MSP · <Company>»

### День 1 — подготовка
- [ ] Создан файл `clients/<slug>.yml` из шаблона
- [ ] Создан Bastion WireGuard peer для клиента (cfg + qr)
- [ ] Предоставлен клиенту WG-конфиг (через Bitwarden send)
- [ ] Получены от клиента:
  - [ ] SSH/RDP админ-доступ на 1 представительный сервер
  - [ ] Список серверов (inventory)
  - [ ] Имя ответственного за IT (телефон, email, TG)
- [ ] Согласовано окно работ (обычно вне рабочего времени клиента)

### День 2 — развёртывание
- [ ] WireGuard клиент поднят на сервере клиента, tunnel up
- [ ] `install_linux.sh` / `install_windows.ps1` отработал на всех серверах
- [ ] Все targets в Prometheus `up == 1`
- [ ] `bronze_alerts.yml` подхвачен (`promtool check rules`)
- [ ] Alertmanager route настроен на Telegram-чат клиента
- [ ] restic бэкап первый раз выполнен
- [ ] restic restore тестового файла — OK

### День 3 — калибровка и передача
- [ ] Пороги алертов откалиброваны под реальный профиль нагрузки
- [ ] Grafana dashboard расшарен клиенту (view-only link)
- [ ] Тестовый алерт отправлен → клиент подтвердил получение
- [ ] Первый weekly-report сгенерирован и отправлен (пусть частичный)
- [ ] В Notion создана страница клиента с ссылками

### DoD
- [ ] Клиент подписал «Акт о начале оказания услуг»
- [ ] Выставлен счёт за разовый «запуск» (15–25k ₽)

## Приём нового клиента — Silver

Длительность: 5–7 рабочих дней.
Базу (как в Bronze) **сначала** + дополнительно:

### День 4 — автоматизация
- [ ] Подняты Automation VM (Puppet + Ansible control)
- [ ] Собран ssh-inventory в Ansible (`hosts.ini`)
- [ ] Prerequisites для Puppet: bolt/агенты установлены
- [ ] Первый pull конфигов — ansible-playbook deploy_silver.yml --check

### День 5 — Loki + Promtail
- [ ] Loki развёрнут на Automation VM
- [ ] Promtail установлен на всех клиентских серверах
- [ ] Логи видны в Grafana → Explore → Loki

### День 6 — AD/GPO (если есть)
- [ ] Сделан бэкап всех существующих GPO
- [ ] Baseline-GPO применена в отдельном OU (для тестов)
- [ ] Согласован план миграции существующих юзеров/компов в baseline-OU

### День 7 — обучение клиента
- [ ] Провели 1-часовой zoom: как читать dashboard, что делать при алерте
- [ ] Передали ссылки на runbook'и
- [ ] Назначили ответственного L1 со стороны клиента для коммуникации

## Еженедельная проверка клиента

Каждый пятница, 14:00–16:00.

- [ ] `verify_all.sh <tariff>` → без ошибок
- [ ] Uptime по каждому серверу ≥ плановый SLA
- [ ] restic check last snapshot → OK
- [ ] По одному случайному файлу сделан restore в `/tmp/verify/<date>/`
- [ ] Grafana → Dashboards: нет жёлтых/красных панелей > 10% времени
- [ ] Loki (Silver+): нет неожиданных скачков ERROR-событий
- [ ] Wazuh (Gold): нет новых Critical-алертов без response
- [ ] Сгенерирован weekly-report.pdf
- [ ] Отправлен клиенту в Telegram + email до 17:00 понедельника
- [ ] В Notion обновлена страница клиента

## Ежемесячный restore drill

1-е число каждого месяца. 1–2 часа на клиента.

- [ ] Выбрана случайная БД/файловая папка
- [ ] Восстановление в изолированную sandbox-VM
- [ ] Функциональный тест:
  - Open 1С (база) — юзер работает?
  - File server — случайный документ открывается?
  - Веб-сайт — поднимается в staging, страницы открываются?
- [ ] Отчёт в Notion: дата, что восстанавливалось, занятое время, наблюдения
- [ ] При проблеме — P1 тикет к senior

---

## Ежеквартальная ревизия

- [ ] Аудит admin-доступов клиента (кто сейчас админ, чужих убрать)
- [ ] Ротация паролей мониторинг-юзеров (`mspshield_mon` в БД, `monitor` в AD)
- [ ] Ротация ключа restic (S3-креды, encryption-password)
- [ ] Обновление ОС на Monitoring/Automation/Wazuh VM (dnf upgrade security-only)
- [ ] Проверка лицензий (1С, Windows Server, KES — сроки действия)
- [ ] Проверка DR-плана: сколько времени занимает полный rebuild monitoring VM
- [ ] Ревизия alert rules: какие WARN превратить в INFO, какие CRIT в WARN

## Инцидент P1 (runbook)

### T+0 — триггер
- [ ] Alert пришёл в `#incidents` Telegram-чат
- [ ] Dedicated on-call инженер делает `/ack <alert_id>`

### T+5 — первичная диагностика
- [ ] Открыт тикет в osTicket (Gold) или Notion (Bronze/Silver)
- [ ] Определён affected service + скоп («только 1С» / «всё у клиента»)
- [ ] Клиенту отправлено: «Видим проблему X, работаем. Апдейт через 30 мин»

### T+15…60 — митигация
- [ ] Выполнены первые 5 шагов из соответствующего runbook из [`TROUBLESHOOTING.md`](./TROUBLESHOOTING.md)
- [ ] Если нужно — поднят senior (эскалация)
- [ ] Клиенту апдейт: либо resolved, либо «работаем, ETA X мин»

### T+60+ — если не решено
- [ ] Эскалация к владельцу MSPShield
- [ ] Если сервис лёг из-за стороннего вендора (хостер, Yandex Cloud) — канал у провайдера
- [ ] Бизнес-решение: workaround (временное обходное)

### После восстановления
- [ ] Post-mortem в Notion в течение 48 часов
- [ ] Обновление runbook'а, если процедура не помогла
- [ ] При необходимости — compensation клиенту (SLA credits)

## Расторжение договора

Триггер: уведомление клиента (≥ 30 дней по договору).

### T-30 — получение уведомления
- [ ] Подтверждён factical срок окончания
- [ ] В календаре отмечена дата «Client offboarding: <slug>»
- [ ] В Notion обновлён статус клиента

### T-14 — передача материалов
- [ ] Экспорт конфигов из git bundle
- [ ] Ключи WireGuard + SSH на архив
- [ ] Последние 3 restic snapshots + пароль в Bitwarden Send (одноразовый)
- [ ] Документация (Notion страница → PDF export)
- [ ] Ссылка на Grafana-snapshot (сохранить snapshot.json)

### T-7 — совместный звонок
- [ ] Клиент получил материалы, убедились что всё открывается
- [ ] Ответы на вопросы
- [ ] Обсуждён NDA-период (ПДн удаляем через 30 дней)

### T+0 — в день прекращения
- [ ] Отключён мониторинг (prometheus.yml — удалить targets клиента)
- [ ] Отозваны WireGuard ключи
- [ ] Остановлены systemd timers бэкапов
- [ ] Клиент получил «Акт о прекращении услуг»

### T+30 — окончательная очистка
- [ ] Удалены все данные клиента с наших серверов
- [ ] S3 бакет очищен (`rclone purge`)
- [ ] Клиенту прислан «Акт об удалении ПДн»
- [ ] Папка `clients/<slug>/` в git переименована в `archive/<slug>_<date>/`
