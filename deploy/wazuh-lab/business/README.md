## Состав и контракт

- `rules.xml`: только наш диапазон 100200–100208; штатные правила не переписываются.
- `scenarios.json`: восемь отклонений и четыре контрольных случая с ожидаемыми ID.
- `generate.py`: пишет JSONL, две строки формата sshd и меняет безвредный файл FIM. Не выполняет входы, атаки или действия над клиентами.
- `dashboards.py`: 14 объектов — представление индекса, метрики, поиски и три панели. Данные не генерируются визуализацией.
- `apply.py`: backup, добавление двух источников, правило, проверка и точечный restart manager, сохранение объектов через API.
- `verify.py`: сравнение каждого case/run_id с ожидаемым правилом, штатных SSH и наличие панелей.
- `repair_metrics.py`: точечное исправление параметров числовых карточек с резервной копией; не перезапускает manager.

## Нормализованный формат

`msp.schema=msp-client-v1`, `msp.synthetic=true`, `tenant`, `asset`, `event`, `status`, `approved`, `run_id`, `case`, `source`, `observed_at`. В индексированном alert они находятся под `data.msp.*`.

`approved` — строка `true/false`, не самостоятельная проверка разрешения. В настоящем проекте доверенный преобразователь должен получать её из реестра согласований. Эта лабораторная версия правила требует synthetic=true и не выдаётся за боевой детектор. Для реальных данных — отдельная схема/набор правил с аутентифицированным источником, проверками полноты и ложных срабатываний.

## Выполнение на учебной VM

```bash
sudo python3 /home/service/wazuh-lab/business/apply.py
# Дождаться запуска чтения новых источников, затем:
sudo python3 /home/service/wazuh-lab/business/generate.py
sudo python3 /home/service/wazuh-lab/business/verify.py
```

Обычное упражнение повторяет только generate/verify. `apply` перезапускает manager; согласовать паузу сбора. `business-last-run.json` хранит текущий run, `business-verification.json` — сравнение. Первые записи, созданные до начала чтения файла, могут быть пропущены: не выдавать наличие файла за end-to-end результат.

## Панели

- `/app/dashboards#/view/msp-business-overview` — общий контроль.
- `/app/dashboards#/view/msp-business-continuity` — копирование, восстановление, доступность учёта.
- `/app/dashboards#/view/msp-business-security` — права, защита, изменения, штатные SSH/FIM.

**Все панели учебные.** Счётчики включают выбранный период, а не только последний запуск. Для точного прогона использовать `data.msp.run_id` в поиске; он не подходит для штатного SSH/FIM, где связь по отдельному вымышленному пользователю/пути и времени. Фильтр tenant не является RBAC/изолированным пространством клиента.

## Возврат

Перед применением: `/home/service/wazuh-lab/business-backups/<UTC>/`. Там исходный manager config, прежнее правило при наличии и экспорт ранее существовавших известных объектов. Восстановить исходную конфигурацию **и effective `/var/ossec/etc/ossec.conf`**, прежний rules file или убрать только новый, проверить `wazuh-analysisd -t`, перезапустить manager. Панели импортировать из прежнего NDJSON либо удалить только новые ID `msp-business-*`, если их раньше не было. Историю alerts не удалять ради отката правил.

Если применение панелей завершилось ошибкой, правила уже могут быть применены — inspect/verification перед повтором. Не выполнять `down -v`, не менять штатные `wazuh-alerts` templates и не включать Active Response. Индексатор и dashboard не требуют перезапуска для добавления saved objects.
