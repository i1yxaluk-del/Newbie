# 3. Разобранные задачи проекта

## Случай 1. Установить резервное копирование

Источник: `technical/0_Common/ansible/roles/restic_client/`. Откройте по порядку `defaults/main.yml` → `tasks/main.yml` → `templates/mspshield-backup.sh.j2`.

**Зачем:** настроить программу, доступ к хранилищу и расписание одинаково на согласованных узлах. `restic_repository` определяет хранилище, `restic_password` — ключ шифрования репозитория, `restic_s3_*` — права обращения к S3; одно не заменяет другое. `restic_paths` выбирает данные, `restic_schedule` — время, `restic_randomized_delay` — случайную задержку, чтобы все узлы не начали загрузку одновременно.

**Как работает:** проверки входов → пакет → закрытый каталог `/etc/restic` → файл окружения → сценарий → systemd-служба → таймер. Служба читает `EnvironmentFile`, затем запускает файл. Шаблон сам по себе не выполняет backup. Таймер с `Persistent=true` может выполнить пропущенный запуск после включения.

**Что найдено при разборе:** существующая роль включает таймер до проверки/инициализации репозитория; `restic snapshots || restic init` смешивает отсутствие репозитория с сетевой ошибкой и неверным ключом. Эти ветви нельзя считать взаимозаменяемыми. На учебной копии сначала отдельно подтвердить доступ и подготовку, затем включать расписание. Эта роль не заменяет production `migration/restic-backup.sh`, у которого другие пути и формат комплекта.

**Практика:** составить таблицу «задача → создаваемый файл → кто читает → проверка». Наставник показывает синтетическую ошибку ключа, ученик объясняет остановку без нового `init`. Успех — согласованный backup и прикладное восстановление; `enabled=true` таймера недостаточно.

## Случай 2. Метрики и журналы

Источник: роль `monitoring_agent`. `node_exporter` читает метрики ОС, Prometheus их запрашивает; Promtail отправляет журналы в Loki. Это два разных потока. Разрешение TCP/9100 от выбранной подсети нужно для сборщика, а не для всех посетителей интернета.

Сравнить: пакет → systemd → UFW-правило → загрузка Promtail → конфигурация → `notify` обработчику. В имеющемся `creates` проверяется наличие пути бинарного файла, а не его версия: изменение номера версии может не заменить установленную программу. Загрузка без checksum также не доказывает подлинность файла. Promtail — устаревающий компонент: перед новым внедрением проверить поддерживаемый сборщик и путь миграции, а не копировать старую роль вслепую.

**Практика:** нарисовать зависимости «узел → exporter → сеть → Prometheus → Grafana» и «файл журнала → сборщик → Loki → поиск». При пустой панели найти первое отсутствующее звено. Не открывать порт всему миру, чтобы убрать симптом.

## Случай 3. Укрепить SSH

Роль `baseline` отключает парольный вход, ограничивает пользователей, меняет UFW и вызывает перезапуск SSH. `validate: sshd -t` проверяет синтаксис файла, но не доказывает, что ваш ключ разрешён, пользователь указан верно и новый сетевой маршрут доступен.

**Правильный порядок:** разрешение → проверенная консоль восстановления → вторая рабочая SSH-сессия → ключ и нужный пользователь → изучение итоговых правил → один тестовый узел → новая проверка входа. Только после этого расширять применение. Никогда не использовать действующую Astra Wazuh для первого упражнения этой роли.

**Отказ:** если потеряна связь, `ignore_errors` её не вернёт. Использовать заранее проверенную консоль/откат, зафиксировать время и причину; не повторять сценарий на остальных узлах.

## Случай 4. Обновить пакеты

В `patch_nondisruptive.yml` название «без перезагрузки» не означает «без простоя»: пакетный установщик может перезапустить службу. `autoremove` может удалить пакеты, считающиеся неиспользуемыми. В `patch_disruptive.yml` проверка `/var/run/reboot-required` подходит не всем ОС; `systemctl is-active` не проверяет работоспособность приложения.

Ученик должен составить перечень ОС, пакетов, приложений, резервных копий, окна и прикладных проверок. `serial: 1` оставляет одновременность один узел, но сценарий всё ещё может последовательно затронуть всех клиентов. Указанный в комментарии автоматический cron/CI запуск нужно подтвердить реальной настройкой; комментарий не является расписанием.

## Случай 5. Ansible изменил файл — Wazuh сообщил об этом

Это нормальная связь управления конфигурацией и наблюдения. Ansible знает **намерение изменения**, Wazuh фиксирует **наблюдаемое событие**. Ни одна система сама по себе не доказывает разрешение.

В изолированном упражнении наставник заранее указывает разрешённый путь FIM. После изменения связать: заявка/разрешение → время запуска Ansible → ожидаемый файл/hash → событие FIM → проверка результата. Не применять учебный `practice.yml` к Wazuh-контейнеру автоматически: он работает в собственном `/tmp` и не создаёт Wazuh-события без отдельного подключения источника.

**Лучший результат:** событие объяснено и связано с заявкой. **Плохой результат:** полностью выключить FIM, потому что разрешённые изменения создают шум. Лучше уточнить перечень путей, частоту, группировку и процедуру рассмотрения исключений.
