# GitHub для владельца MSPShield

## Зачем владельцу GitHub

Git хранит историю решений, GitHub добавляет совместную проверку, автоматические проверки (CI) и права доступа. Владелец отвечает за то, чтобы изменение было объяснимым, проверенным и обратимым. Сначала [учебная глава](../chapters/03-git-ci.md); команды ниже выполняются после проверки своего состояния и разрешения на публикацию.

## Рабочая модель

- `main` — интегрированное состояние, а не место для экспериментов.
- Ветка (branch) — отдельная линия изменения с одной целью.
- Коммит (commit) — законченная версия выбранных изменений.
- Запрос на включение (pull request) — контекст, риски, проверки и обсуждение.
- Автоматическая проверка (check) подтверждает выбранное условие, не полную готовность услуги.
- Метка версии (tag) — точка, которую сопоставляют с реально опубликованной сборкой.

## Ежедневный цикл

```bash
git status
git fetch origin
git switch main
git pull --ff-only
git switch -c docs/update-runbook
# изменить файлы
git diff --check
git diff --stat
git add docs/
git commit -m "docs: уточнить восстановление Mongo"
git push -u origin docs/update-runbook
```

`--ff-only` запрещает скрыто создать merge при pull. `diff --check` ловит часть ошибок форматирования. Перед `add` просмотрите полный diff и убедитесь, что в нём нет `.env`, session database, token или клиентских данных.

## Pull request Owner-review

Описание PR отвечает на пять вопросов:

1. Какая проблема подтверждена?
2. Что изменено и что намеренно не изменено?
3. Как воспроизведена проверка?
4. Какой риск и rollback?
5. Какие документы, обучение и monitoring должны измениться вместе с кодом?

Перед merge Owner проверяет scope, CI, секреты, обратимость, совместимость с runbook и влияние на клиента. Зелёный CI не заменяет restore, внешний scan или legal review.

## Конфликт и откат

Конфликт означает, что Git не может автоматически совместить две истории. Сначала поймите обе стороны; не нажимайте «accept current» вслепую. Для уже опубликованного изменения используйте `git revert <sha>` — новый commit сохраняет аудит. `reset --hard` допустим только на собственной локальной ветке после осознанной проверки потерь.

## Практикум

1. Создайте учебную ветку и измените одну строку runbook.
2. Откройте PR с risk/rollback.
3. Создайте конфликт в другой ветке и разрешите его вручную.
4. Слейте PR, затем сделайте revert.
5. По истории объясните, кто, зачем и каким evidence подтвердил изменение.
