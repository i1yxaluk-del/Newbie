# 2. Практикум Wazuh

[← Курс](README.md) · [Архитектура](01_BASICS.md) · [Далее: клиент](03_CLIENT_READINESS.md)

На Astra `192.168.114.10`; команды выполняет наставник/оператор через проверенный SSH. Локальная рабочая станция не является manager. До задания проверить hostname и каталог, не печатать `credentials.json`, env или rendered Compose.

## Lab 1 — пройти путь события

1. Открыть Wazuh → **Threat Hunting / Поиск угроз**, выбрать последние 24 часа.
2. Фильтр `rule.groups: msp_lab` (используйте поле и значение в UI, если синтаксис поиска отличается).
3. Найти правила 100100–100103, раскрыть событие. Записать `timestamp`, `rule.id`, `rule.level`, `agent.id`, `data.synthetic`, `data.scenario`, `data.run_id`, `location`.
4. Объяснить: `agent.id=000` — manager, `synthetic=true` — учебный сигнал. Не оформлять его как реальный инцидент клиента.

**Успех:** найдены четыре сценария baseline/backup_failed/access_review/policy_drift и прослежено одно событие до raw JSON. **Нет результата:** проверить период/часовой пояс и фильтр, затем manager→Filebeat→indexer; не отключать auth.

## Lab 2 — сгенерировать новый набор

На VM, только в лаборатории:

```bash
sudo python3 /home/service/wazuh-lab/runbook/wazuh-lab-events.py
sudo python3 /home/service/wazuh-lab/runbook/wazuh-lab-verify.py
```

Первая команда дописывает четыре JSONL-события и меняет один файл FIM в `training/`. Она не выполняет атаку. Скопировать только `run_id`, подождать индексацию и найти **новый** набор по нему. При задержке повторить verify, а не generator: иначе получите другой run и дубли упражнения.

**Успех:** для данного run_id найдены 4 события с ожидаемыми rule IDs. Общий счётчик `≥4` недостаточен: это может быть прошлый запуск. **Откат:** события остаются учебной историей; не удалять общие индексы для очистки четырёх записей.

## Lab 3 — FIM

После Lab 2 найти FIM-событие для `/var/ossec/lab/fim/training-policy.txt`. Проверить время baseline scan: первый файл может дать событие добавления, следующий запуск — изменения. Сравнить атрибуты/контрольные суммы в доступных полях и связать с разрешённым упражнением.

**Успех:** найдены путь и факт изменения. Не считать произвольный JSON со словом FIM настоящим syscheck event. При отсутствии события наставник проверяет состояние syscheck и startup scan; не добавлять `/` host в monitoring ради теста.

## Lab 4 — SCA и inventory

В Configuration Assessment открыть policy и определить проверяемую ОС. В IT Hygiene найти inventory manager. В отчёте явно указать: это container endpoint, host Astra не оценён как зарегистрированный agent.

**Успех:** корректно установлены объект и границы оценки. **Критическая ошибка:** перенос CIS-рекомендации в production/host без анализа и разрешения.

## Lab 5 — отказ UI без вмешательства в сбор

Наставник описывает симптом «dashboard не открывается». Junior сначала составляет read-only план: сеть/TLS → dashboard → indexer → manager/Filebeat, определяет порядок эскалации. Реальные остановки только по отдельному разрешению наставника и исключительно lab-сервисов. `docker system prune`, удаление volume и reset passwords не являются диагностикой.

**Успех:** план различает недоступность отображения и потерю данных, содержит stop-condition и rollback. Фактический эксперимент не обязателен без согласованного окна.
