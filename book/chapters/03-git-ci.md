## Что хранит Git

Git хранит версии файлов и связи изменений. Рабочая папка — ещё не опубликованная версия. `git status` перечисляет отличия, `git diff` показывает строки; обе команды только читают. Коммит фиксирует выбранное изменение локально, push отправляет его на удалённый сервер. Ни одна из этих операций сама по себе не публикует сайт на VM.

GitHub добавляет совместное обсуждение, запросы на включение изменений и автоматические проверки. Владелец отвечает за смысл: что изменилось, зачем, как проверено и как вернуться. Маркетолог может менять текст, но изменение цены требует сверки прайса, JSON лендинга, SEO-разметки, публичных условий, бота и договора.

## Сборка и проверки

CI — автоматическая проверка после публикации изменений. В `.github/workflows/quality.yml` заданы конкретные задания, а не универсальное доказательство качества. Проверка ссылок не тестирует регистрацию в Matrix, сборка React не проверяет отправку письма, синтаксис Bash не выполняет восстановление.

Секреты нельзя помещать в историю даже «на минуту»: удаление строки следующим коммитом не удаляет предыдущую версию. Файлы `.env`, личные сессии и реальные клиентские сведения хранятся вне публичного Git.

## Возврат изменения

Для общего опубликованного изменения обычно создают новый обратный коммит, сохраняя историю. Смена статических файлов сайта требует отдельного резервного каталога; откат БД — отдельной совместимой процедуры. «Вернули Git» не означает, что данные приложения возвращены.

## Практика и результат

В отдельном учебном репозитории создать файл, посмотреть diff, зафиксировать, изменить и отменить обратным коммитом. Затем заполнить карточку публикации текста: исходный источник → проверка → коммит → доставка сборки → внешний HTTP → проверка содержимого. Не включайте живые credentials ради примера.
