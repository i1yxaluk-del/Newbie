# Почта, Stalwart, Postbox и проверка доставки

## Письмо проходит несколько систем

Приложение формирует письмо → SMTP принимает отправку → исходящий сервер выбирает маршрут → сервер получателя принимает/отклоняет → фильтр помещает письмо в папку. Подтверждение SMTP не гарантирует попадание во «Входящие» или чтение человеком.

Stalwart хранит почтовые данные и настройки, обслуживает отправку/получение в выбранном профиле. Postbox — отдельный внешний маршрут отправки. В конфигурациях проекта встречаются оба пути: прямой MX после Cloud.ru и Postbox для отдельных отправителей/контуров. Реальный маршрут проверяется для каждого источника, а не определяется названием каталога.

## DNS и доверие

MX указывает принимающий сервер домена. SPF описывает разрешённые источники отправки; DKIM подписывает сообщение, DMARC задаёт политику проверки соответствия домена. PTR связывает обратное имя IP и важен для прямого SMTP. Запись Postbox CNAME не создаёт подпись Stalwart при прямом MX: нужны разные ключи/настройки.

TLS защищает транспорт, но не заменяет проверку домена. Пароль SMTP, API-key Postbox и service-account ID — разные сущности; неправильный вид идентификатора может дать 535. Не менять пароли всех сервисов по одному сообщению, сначала определить точный отправитель и ответ сервера.

## Восстановление и маркетинг

У Stalwart нужны оба согласованных тома. Пустые данные могут вернуть сервис в первичную настройку, хотя контейнер запущен. После restore проверяют ящик, вход и реальную доставку. Массовая реклама требует отдельного согласия и правил отправки; рабочий SMTP не даёт разрешения рассылать рекламу по найденным адресам.

Практика: карта одного письма-заявки и одного incident-письма, источник credentials без значений, маршрут, записи DNS, приём/папка/ответ. Учебные материалы и честные ограничения видео — [почта](../VIDEO_GUIDE.md#облако-и-рабочие-инструменты).
