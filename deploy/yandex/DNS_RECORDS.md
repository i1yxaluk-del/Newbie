# DNS-записи для почты: аудит, безопасность и минимизация

Контекст: домен `msp-claude.online`. Раньше почта шла через **Yandex Cloud Postbox**
(6 записей). Сейчас — **прямая доставка Stalwart по MX** (Cloud.ru, порт 25 открыт).
Stalwart умеет генерировать «идеальный» полный набор из **21 записи** — но большинство
из них необязательны. Ниже разбор и минимальный набор.

## Полный набор от Stalwart (21 запись) и вердикт

| # | Запись | Назначение | Нужна? |
|---|---|---|---|
| 1 | `@` **MX 10** `mail.msp-claude.online` | приём почты | **ДА** |
| 2 | `mail` **A** `45.132.176.143` | адрес MX/HELO | **ДА** (уже есть) |
| 3 | `@` TXT `v=spf1 mx -all` | SPF: кто вправе слать от домена | **ДА** |
| 4 | `v1-rsa-20260521._domainkey` TXT | DKIM (RSA-2048) | **ДА** |
| 5 | `v1-ed25519-20260521._domainkey` TXT | DKIM (ed25519) | можно (2-й селектор) |
| 6 | `_dmarc` TXT `v=DMARC1; p=…; rua=…` | DMARC-политика | **ДА** |

| 11 | `mta-sts` CNAME `mail…` | хост политики MTA-STS | нет* |

Либо заводим файл, либо запись не создаём (рекомендую второе).

## Рекомендуемый минимальный набор — **6 записей**

```
@                              MX   10 mail.msp-claude.online.
mail                           A        45.132.176.143
@                              TXT      "v=spf1 mx -all"
v1-rsa-20260521._domainkey     TXT      "v=DKIM1; k=rsa; h=sha256; p=MIIBIjANBg…"
_dmarc                         TXT      "v=DMARC1; p=quarantine; rua=mailto:alert@msp-claude.online; adkim=r; aspf=r; fo=1"
(обратная зона / PTR)                    45.132.176.143 -> mail.msp-claude.online
```

Опционально (по желанию):
- `v1-ed25519-20260521._domainkey` TXT — второй DKIM-селектор (современный ed25519).
- `@` CAA `0 issue "letsencrypt.org"` — **без** `accounturi=…`.

## Что удалить из текущего DNS (осталось от Postbox)

| Запись | Действие |
|---|---|
| `@` TXT `v=spf1 include:postbox.cloud.yandex.net ~all` | **заменить** на `v=spf1 mx -all` |
| `egtn6ichfrjtq1kcmeki-1._domainkey` CNAME → `…dkim.pstbx.ru` | **удалить** |
| `egtn6ichfrjtq1kcmeki-2._domainkey` CNAME → `…dkim.pstbx.ru` | **удалить** |
| `_dmarc.msp-claude.online` TXT (второй, дубль) | **удалить** — оставить один `_dmarc` |
| `_dmarc` TXT | обновить значение (см. ниже) |
| `@` MX 10 mail.msp-claude.online | **оставить как есть** ✓ |

> Про дубль `_dmarc`: в панели регистратора видно два TXT — `_dmarc` и `_dmarc.msp-claude.online`.
> Если поле хоста подставляет домен автоматически, вторая запись превращается в
> `_dmarc.msp-claude.online.msp-claude.online` — бесполезную. **Оставить одну.**

## Безопасность: что и почему

1. **SPF: `-all` вместо `~all`.** Postbox использовал `~all` (softfail — «наверное, не наш»),
   это слабее. Теперь мы сами владеем отправляющим IP, поэтому корректно **жёстко** `-all`.
   `mx` в SPF разрешает ровно хост MX (`mail.msp-claude.online` = `45.132.176.143`) — этого достаточно.
2. **DMARC: начать с `p=quarantine`, потом `p=reject`.** Старое значение было `p=none`
   (только наблюдение — злоумышленник может слать от имени домена безнаказанно).
   Stalwart предлагает сразу `p=reject` (самое строгое). Рекомендую **`p=quarantine`** на
   время обкатки (1-2 недели отчётов), затем `p=reject`: иначе есть риск резать легитимные
   письма из-за недонастроенного SPF/DKIM. `adkim=r`/`aspf=r` (relaxed) достаточно.
3. **DKIM: два селектора не обязательны.** Достаточно RSA-2048 (поддерживают все).
   ed25519 — современнее и короче, но не везде исторически поддержан. Если хочется
   минимума — оставьте только RSA.
   ⚠️ **Ротация ключей:** Stalwart настроен на авто-ротацию раз в 90 дней, а селектор
   содержит дату (`v1-rsa-20260521`). Значит **раз в 90 дней запись DKIM надо обновлять**,
   иначе подпись перестанет сходиться. Варианты: (а) завести напоминание и обновлять
   руками; (б) отключить авто-ротацию в Stalwart и ротировать вручную; (в) автоматизировать
   обновление через DNS-API. Автоматизации через Cloud.ru Evolution DNS API **нет** —
   с текущими ключами он недоступен, поэтому реалистично (а) или (б).
4. **CAA — да, но без `accounturi`.** CAA запрещает чужим CA выпускать сертификаты на домен —
   полезный контроль. Но сгенерированная запись прибита к конкретному **аккаунту** Let's Encrypt;
   при смене аккаунта выпуск сертификатов сломается. Безопаснее `CAA 0 issue "letsencrypt.org"`.
5. **`postmaster@` — важный момент.** Stalwart подставил в `rua=` адрес
   `postmaster@msp-claude.online`, **но такого ящика нет** (на сервере только
   `admin@`, `sales@`, `alert@`) → отчёты DMARC/TLS-RPT будут отскакивать.
   Плюс по RFC 5321 §4.5.1 **любой домен обязан принимать почту для `postmaster@`**.
   Рекомендация: либо **завести `postmaster@`** (алиас на `admin@`), либо указать в
   `rua=` существующий `alert@`. Первое — правильнее.
6. **Не создавать лишнее.** SRV/autoconfig/autodiscover/ua-auto-config нужны только для
   автоматической настройки клиентов; при ручной настройке (imap `993`, smtp `465`) они
   не нужны. MTA-STS/TLS-RPT — опциональный мониторинг, добавляют обслуживание.

## PTR (обратная зона) — только через консоль

С текущими API-ключами обратную зону создать **нельзя**: Cloud.ru Evolution DNS API
недоступен (все пути → `Not Found`), а compute-API не принимает `reverse_dns`
(`extra_forbidden`). Terraform-провайдер `cloudru/cloud` v2.1.3 PTR-зон тоже не имеет
(есть только `dns_public_zone`/`dns_private_zone`).

Сейчас PTR публичного IP = `msp-cloud-vm` (имя ВМ) — для почты это плохо
(приёмники любят PTR, совпадающий с HELO/EHLO или с MX).

Порядок в консоли **Cloud.ru → Evolution DNS → Обратные зоны**:
1. «Создать обратную зону» для сети `176.132.45.in-addr.arpa` (или по инструкции консоли).
2. «Создать запись обратной зоны»: `143` → `mail.msp-claude.online.`
3. Проверка: `nslookup 45.132.176.143` → `mail.msp-claude.online`.
