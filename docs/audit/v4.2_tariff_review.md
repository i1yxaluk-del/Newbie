### 2.1 Архитектура и стоимость

Silver = Bronze + Loki+Promtail + Puppet Server + Ansible Control + AD/GPO скрипты.

**Инфраструктурная стоимость:**

Отпускная цена Silver — 50 000 ₽/мес. При 5 клиентах инфра-расход/клиент ≈ 1 300 ₽ → маржа ≈ 97%.

### 2.3 Валидация

- `technical/2_Silver/EXECUTOR/silver_alerts.yml` — **✅ 10 rules, promtool OK**.
- `deploy_silver.yml` — структурно валиден, но ссылается на роли, которые в репо отсутствуют (ожидаемо, gap из v4.2_report.md).

### 2.4 Puppet — нужен ли в Silver?

Это самый спорный пункт аудита. Puppet Server требует:
- Отдельного CA (внутренний PKI, ротация серверных/клиентских сертификатов)
- Cron-режим запуска (30-мин интервалы)
- Знания языка Puppet DSL + Hiera + модульной структуры
- Отдельной Automation VM (1 900 ₽/мес)

Для 1 человека с 3–5 Silver-клиентами **Ansible-only перекроет 90% use-cases** (push-модель, никакого CA, идемпотентные playbooks). Puppet имеет смысл только если:
- клиентов >10 и нужен pull-режим (клиент сам тянет конфиг при старте VM)
- есть compliance-требование desired state

**Рекомендация:** отметить Puppet как OPTIONAL в Silver.md §1 (ADDON вместо core), core оставить: Loki+Promtail+Ansible-Control+AD/GPO-скрипты. Снимает нагрузку на оператора на ~4 часа/неделю в период до 10 клиентов. При необходимости Puppet включается добавочным спринтом позже.

### 2.5 AD/GPO скрипты (PowerShell)

- `gpo_baseline.ps1` — применяет Baseline GPO (password policy, screen lock, RDP restrictions).
- `install_puppet_agent_windows.ps1` — тривиальная обёртка MSI.
- `kes_deploy_gpo.ps1`, `monitor_kes.ps1` — Gold, см. §3.

**Не проверены синтаксически** — `pwsh` не установлен на audit VM. Рекомендация: добавить в env-setup install `powershell-*` пакета (pwsh 7+) и повторить проверку перед выходом на первый Silver-клиент с AD.

### 2.6 Реализуемость для 1 чел (Silver)

| Операция | Оценка | Риск |
|---|---|---|
| Апгрейд Bronze→Silver для клиента | 6–10 часов | средний: Loki-retention может съесть диск, Puppet-cert не подписывается |
| Настройка AD/GPO на контроллере клиента | 2–4 часа | высокий: `powershell execution policy`, группы безопасности |
| Ежедневный monitoring (Loki alerts + Puppet reports) | +15 мин/день | низкий |

Вывод: **Silver посилен, но ощутимо сложнее Bronze**. Реалистичный порог: не запускать Silver до момента, когда Bronze работает стабильно 2+ месяца без инцидентов. Puppet — отдельный порог: не включать до 3-го Silver-клиента.

## 3. Gold

### 3.1 Архитектура и стоимость

Gold = Silver + Wazuh (SIEM/FIM/vuln-scan) + Kaspersky KSC+KES + osTicket.

**Инфраструктурная стоимость:**

| Компонент | Спеки | ₽/мес |
|---|---|---:|
| Monitoring VM | 4 vCPU, 8 GB | ~3 800 |
| Automation VM | 2 vCPU, 4 GB | ~1 900 |
| Bastion VM | 1 vCPU, 2 GB | ~600 |
| **Wazuh VM** | **8 vCPU, 16 GB, 100 GB SSD** | **~8 500** |
| Object Storage | ~300 ГБ | ~300 |
| **Итого при 15+ клиентов** | | **~14 800** |

Отпускная цена Gold — 85 000 ₽/мес. При 3 Gold-клиентах инфра/клиент ≈ 4 900 ₽ → маржа ≈ 94%. **Но:** см. §3.3 про KSC.

### 3.2 Wazuh

- **Версия в конфиге:** `wazuh/wazuh:4.7.x` (из osticket-comment-compose — не проверено, т.к. Wazuh compose inline в SOP). Актуальная LTS — 4.9.x (вышла Q1 2026).
- **ossec.conf** — синтаксически XML, не валидирован (`xmllint` не установлен на VM). Рекомендация: добавить `libxml2-utils` в env-setup.
- **Нагрузка на оператора:** Wazuh требует ежедневной проверки:
  - уровень/тип алертов (false positives)
  - FIM baseline-обновление после планового патчинга
  - vulnerability-scan результаты (обычно 50–500 уязвимостей на хосте → нужен процесс триажа)

Для 1 человека Wazuh на 3+ клиентах — это **+5 часов/неделю** на обработку алертов и триаж уязвимостей. Это плюсом к существующей P1-нагрузке.

**Альтернативы, требующие меньше внимания:** для 1–2 Gold-клиентов можно заменить Wazuh на простой Falco+Grafana+Loki и pet-проект osquery. Снимает лицензию/экспертизу, но теряет compliance-сертификацию.

### 3.3 Kaspersky (KSC + KES) — критический риск

| Аспект | Реальность |
|---|---|
| Лицензия | **коммерческая**, от 3 500 ₽/узел/год для Endpoint Security Business Select (розница 2026) |
| Дистрибутив KSC | скачивается с support.kaspersky.ru, требует регистрации партнёра |
| Сертификат партнёра Kaspersky | для получения субподрядной скидки — нужен **статус партнёра** (точки, оборот, обучение) |
| Документация в `ksc_setup_guide.md` | описывает интерфейс старой версии KSC (14.2?), актуальная 15.x с принципиально другим UI |
| Поддержка Linux-endpoint | есть, но ограниченно; основной flow — Windows AD через GPO |

**Проблемы для соло-оператора:**
1. **Нет партнёрского статуса** → клиент покупает KES напрямую у Kaspersky, вы только настраиваете. Это ок, но требует координации платежа и передачи ключей.
2. **Цена обучения/сертификации** — Kaspersky регулярно требует re-cert, стоимость курсов 30–80к ₽.
3. **KSC сложен**: иерархия групп администрирования, задачи, тэги, политики — overhead, несопоставимый с уровнем Falco/osquery.

**Рекомендация (важная):**

> Gold в текущей редакции **не реализуем одним человеком без партнёрского статуса Kaspersky**. Варианты:
>
> 1. **Убрать KES из core Gold**, сделать его ADDON (client-provided endpoint protection, мы только подключаем мониторинг). Цена Gold снижается до 70 000 ₽/мес, KSC/KES клиент покупает и обслуживает сам через Kaspersky-партнёра.
> 2. **Заменить KES на альтернативу с partner-friendly моделью:** ESET Protect Entry Cloud (управляется вендором), Dr.Web Enterprise Security Suite (отечественный, 152-ФЗ дружественный, есть российский партнёр-канал).
> 3. **Отложить Gold до партнёрки** — первые 6 мес продавать только Bronze и Silver.
>
> Выбор между 1/2/3 — стратегический. В v4.3 рекомендую **вариант 1 или 3**.

### 3.4 osTicket

- **Версия:** `osticket/osticket:v1.18.1` (в compose). Актуальная 1.18.x, проект живой но медленный release-cycle, legacy PHP 7.4/8.x.
- **Compose:** исправлен (убран `version: "3.8"`). Валидация `docker compose config` проходит с переменными.
- **Альтернативы**, которые проще обслуживать соло: Plane (новее, Python, активное развитие), Zammad (Ruby, более тяжёлый, но фичи богаче). Для начала — osTicket рабочий вариант, не трогать.

### 3.5 Реализуемость для 1 чел (Gold)

| Операция | Оценка | Риск |
|---|---|---|
| Апгрейд Silver→Gold | 12–20 часов | высокий |
| Настройка Wazuh Manager + 5 agents | 3–5 часов | средний |
| Первая настройка KSC | 8–16 часов **при наличии партнёрского статуса**; не реализуемо без него | критичный |
| 24/7 P1 реакция | -3 часа сна/сутки при инциденте | высокий |
| Ежедневный Wazuh triage | 0.5–1 час | низкий |

Вывод: **Gold в текущей редакции нереалистичен для соло-оператора в первые 6 мес.** См. рекомендации в §3.3. Если KES заменить на партнёрский вариант — Gold становится реализуемым с 3-го квартала первого года.

## 5. Документация

### 5.1 Текущая структура

**Две параллельные ветки:**

1. `technical/*/Bronze|Silver|Gold.md` + `CLIENT/SOP_client_*.md` + `EXECUTOR/SOP_executor_*.md` — **технический уровень**, для Junior/Executor.
2. `docs/deployment/` + `docs/lifecycle/` + `docs/runbooks/` + `docs/onboarding/` + `docs/sales/` — **процессный уровень**, для owner/junior + клиентский фронт.

Обе ветки содержат ценный контент, но **не связаны перекрёстно**. Пример: `docs/deployment/landing_production.md` описывает деплой landing, а `technical/1_Bronze/EXECUTOR/SOP_executor_bronze.md` описывает ту же VM'у как Monitoring+Bastion — читатель не поймёт, что это про разные или про одну и ту же VM, пока не прочитает оба документа.
