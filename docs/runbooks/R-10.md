# R-10 · Monthly patch window

**Severity:** P4 (плановые работы)
**Tier:** all
**Time budget:** 2–4 часа на клиента
**Requires:** согласованное окно с клиентом, Ansible inventory

---

## 1. Триггер

Плановое: первая суббота каждого месяца, 22:00–02:00 МСК (или
согласованное окно с клиентом).

---

## 2. Подготовка (за неделю)

- [ ] Просмотреть CVE-feed за месяц (nvd.nist.gov, bdu.fstec.ru, rutvx).
- [ ] Определить applicable patches для клиентских сервисов.
- [ ] Составить runbook «что патчим сегодня» по каждому клиенту.
- [ ] Уведомить клиента за 5 дней: «Плановое окно <дата>, <часы>, возможные перезагрузки».

---

## 3. Подготовка (в день patch-окна)

- [ ] Freshest backup (если vigilant — дополнительный snapshot в cloud).
- [ ] Проверить, что Ansible dry-run проходит на **staging** (у нас внутренний staging).
- [ ] Confirm patch list с клиентом по email/Telegram/MAX (без ответа = подтверждено).

---

## 4. Действия

### 4.1. Non-disruptive patches (сначала)

- [ ] `ansible-playbook playbooks/patch_nondisruptive.yml -e tier=<tier> -e client=<client>`.
  - Обновления, не требующие reboot.
- [ ] Проверить сервисы.

### 4.2. Disruptive patches (с reboot)

- [ ] Rolling по серверам (один за другим).
- [ ] `ansible-playbook playbooks/patch_disruptive.yml -e tier=<tier> -e client=<client> -e batch_size=1`.
- [ ] После каждого reboot: health check (критические сервисы up).
- [ ] Если hear check fails → остановить rolling, не идти дальше.

### 4.3. Database-сервера (особая осторожность)

- [ ] Сначала backup (снапшот + restic).
- [ ] Обновление — в последнюю очередь.
- [ ] Проверка: репликация restarted, master-slave consistent.

---

## 5. Откат

- Если новый патч ломает сервис → `apt-get install <package>=<prev_version>`.
- Если ломает систему → восстановление из snapshot (cloud instance snapshot).

---

## 6. Проверка (после patch window)

- [ ] Все сервисы up, Prometheus green.
- [ ] `uname -a` — ядро обновилось (если ожидалось).
- [ ] Нет новых ошибок в логах за 2 часа после patch.
- [ ] Test critical flow работает (пример: пользователь может залогиниться в 1С).

---

## 7. Коммуникация

- Утро после patch: Telegram/MAX клиенту (в выбранный мессенджер): «Патчи прошли, всё работает. Детали в weekly report».
- В weekly report: перечень установленных патчей с номерами CVE.

---

## 8. Post-actions

- [ ] Patch log пополнен (inventory всего, что установили, когда).
- [ ] Следующий patch window на календаре.
- [ ] Если были сюрпризы — добавить в runbook «особенности клиента X».
