# Wazuh в РФ: задачи бизнеса, источники и проверяемые решения

[← Курс](README.md) · [Практика на платформе](09_BUSINESS_PLATFORM.md)

## Как выбраны задачи

Ниже реальные **типы эксплуатационных проблем**, а не выдуманные истории наших клиентов или оценка размера рынка. Они вытекают из зависимости бизнеса от доступности учётных систем, сохранности данных, управляемости доступа и работы средств защиты. Подтверждённых интервью/оплаченных требований конкретных клиентов в этом комплекте нет: каждый профиль — заготовка для обследования.

Официальные возможности: [сбор журналов](https://documentation.wazuh.com/current/user-manual/capabilities/log-data-collection/monitoring-log-files.html), [FIM](https://documentation.wazuh.com/current/user-manual/capabilities/file-integrity/index.html), [SCA](https://documentation.wazuh.com/current/user-manual/capabilities/sec-config-assessment/index.html), [обнаружение уязвимостей](https://documentation.wazuh.com/current/user-manual/capabilities/vulnerability-detection/index.html). Версия стенда 4.14.5; документация `current` может отличаться. Штатные SSH ID 5715/5760 и FIM 550/553/554 проверяются по установленному набору, не по памяти.

Для работы с ПДн применимы обязанности по организационным/техническим мерам, включая [152-ФЗ, статьи 18.1, 19, 21](https://www.consultant.ru/document/cons_doc_LAW_61801/). SIEM помогает фиксировать и разбирать события, но не даёт автоматическое соответствие закону, сертификацию ФСТЭК/ФСБ, юридическое заключение или замену ответственного оператора. Конкретный набор обязательных мер определяют по системе и её требованиям, не по названию панели.

## Приоритет 1: торговля, бухгалтерское обслуживание, небольшой производитель

Критичная система — учёт/заказы/зарплата, нередко 1С и её БД. Ценность — быстрее узнать о риске потери данных и доказать проверку восстановления, а не обещать «Wazuh спасёт 1С».

| Проблема и последствие | Источник и цепочка решения | Действие ответственного | Как измерять |
|---|---|---|---|
| Задание backup завершилось ошибкой, но никто не заметил | Результат задания → доверенный преобразователь → `backup_job/failed` → правило/очередь обращения | Проверить другую пригодную копию, доступ/объём, назначить повтор; не удалять историю | Доля заданий с полученным результатом, задержка сигнала и начала диагностики |
| Копия «успешна», но восстановление не работает | Отдельная прикладная проверка restore → `restore_check/failed` | Проверить артефакт/ключи/зависимости; остановить принятие недоказанного RTO | Доля пройденных запланированных восстановлений, измеренные RTO/RPO конкретной системы |
| Учётное приложение недоступно | Независимая проверка прикладного запроса → `application_service/unavailable` | Подтвердить влияние, проверить БД/службу/лицензию/сеть | Время обнаружения и фактический простой по независимой проверке |
| Экспорт данных не связан с разрешённой задачей | Реальный журнал приложения и контекст заявки → `application_export`, approved=false | Уточнить основание/пользователя/объём; эскалация, без обвинения в утечке по одному факту | Доля значимых экспортов с известным основанием, время рассмотрения |

**Граница:** Wazuh не создаёт копию, не проверяет автоматически любую конфигурацию 1С и не является DLP. Событие экспорта означает наблюдённую операцию, не доказанную кражу. Для 1С нужны версия платформы, доступные журнал регистрации/технологический журнал, формат и поля, объём/ротация и разрешение на сбор. В комплекте есть нормализованный учебный формат, **готового парсера всех версий 1С нет**.

## Приоритет 2: офис с удалёнными сотрудниками и подрядчиками

| Проблема | Источники | Решение и ограничения |
|---|---|---|
| Бывшему сотруднику сохранили привилегии | Кадровое событие/заявка + AD/локальные учётки + подтверждённое изменение групп | Сопоставление срока отзыва и реального состояния. Сам журнал изменения не доказывает полноту offboarding |
| Администратор изменил права без заявки | Windows Security с нужной политикой аудита либо Linux audit/journal + реестр согласований | Выделить значимое изменение, найти разрешение; не считать клиентское `approved=true` доверенным доказательством |
| Ошибки и успешные входы в удалённое управление | Настоящий sshd/Windows logon журнал | Штатные правила, оценка пользователя/источника/времени. Ошибки входа не равны подтверждённой компрометации |
| Защита рабочих станций отключена/давно не обновлялась | Документированный экспорт/KSC API/журналы конкретного продукта и версии | Сигнал, кто должен восстановить защиту; Wazuh не заменяет Kaspersky и не предоставляет лицензию |
| Перестал поступать журнал с важного узла | Агент/очереди/последнее событие + независимый контроллер состояния | Вычислить устаревание вне молчащего источника, затем прислать `collection_health/stale`. Отсутствие сообщений само по себе правило JSON не обнаруживает |

Пример требования клиента: «изменения привилегий определённых групп рассматриваются в рабочее окно, с резервным ответственным и журналом решения». Перед обещанием нужны определённые группы, реальные данные и проверка ложных срабатываний. Учебный `office-demo` не является настроенной изоляцией реального клиента.

## Приоритет 3: управляемые Linux-серверы, VPN и сайты

FIM отслеживает изменение согласованных критичных файлов. Ansible задаёт желаемую конфигурацию, Wazuh наблюдает факт изменения. Связка полезна для отличия планового изменения от необъяснённого: задача → commit → время/узел/путь → событие → проверка приложения. Она не должна зависеть от команды пользователя «это согласовано» без проверки в реестре работ.

Уязвимости и SCA помогают расставить задачи обновления/укрепления, но требуют правильной ОС, актуального inventory/feed и проверки применимости. CIS-политика контейнерного Amazon Linux на стенде не является оценкой host Astra. Не ставить клиенту Linux-профиль, не проверив поддерживаемые поля и ограничения его агента/дистрибутива.

## Что подготовлено именно на нашей платформе

- Отдельные учебные правила **100200–100208**, два вымышленных клиента `trade-demo` и `office-demo`.
- 8 отклонений + 4 контрольных случая: успешная копия и согласованные изменения/права/экспорт остаются базовым правилом 100200, не «аварией».
- Штатные SSH **5760** (неудача) и **5715** (успех) на фикстурах журналов; это не имитация сетевой атаки.
- Настоящее изменение обычного файла в существующем FIM-каталоге; штатные 550/554 и результат текущего запуска проверяются отдельно.
- Панели используют реальные документы `wazuh-alerts-*`, прошедшие обработку manager, и сохранённые поиски. Тестовые alerts не вставляются напрямую в indexer.

## Переход от шаблона к договору

Для каждой задачи заполнить: владелец процесса → критичная система → настоящий источник/версия → пример без секретов → нормализация → правило → допустимые исключения → канал/ответственный → рабочее окно → проверка → срок хранения/удаления. Начать с 2–3 задач, измерить шум и полноту, затем расширять.

Экономический результат считать по собственным данным клиента: время поиска события до/после, доля пропущенных заданий, длительность ручного отчёта, факт пройденного restore. Не подменять снижение риска количеством alerts и не обещать окупаемость по выдуманной цене часа простоя. Коммерческие ограничения — [прайс/capacity](../../../commercial/PRICING.md).
