## 1. Новая заявка → аудит

**Триггер:** POST в Telegram от `/api/leads`.

**Шаги:**
1. В течение 15 минут (раб.) ответить в мессенджер клиента подтверждением.
2. Предложить слот в календаре (3 варианта в ближайшие 48 ч).
3. За 1 час до созвона — подготовить:
   - DNS-резолюция `company.ru` (whois, SSL-статус)
   - Быстрый внешний Nmap (только для явно публичных IP)
   - Проверку паблик-баз на утечки email клиента
4. Аудит: 30 минут онлайн (Jitsi / Telegram video).
5. По итогам — PDF-отчёт с 3–5 конкретными рисками за 24 часа.

**DoD:** PDF отправлен, следующий шаг согласован (КП или отказ).

## 2. Онбординг нового клиента

**Триггер:** оплачен счёт за первый месяц + разовый запуск.

### День 1. Доступы
- [ ] Получен admin-SSH/RDP на 1 представительный сервер
- [ ] Создан инвентарный файл `/opt/mspshield/clients/<slug>.yml`
- [ ] Заведён чат в Telegram с ответственным клиента

### День 2. Развёртывание
- [ ] Bastion VM в Yandex Cloud поднят (для новых клиентов — выделенный или multi-tenant)
- [ ] WireGuard-tunnel между Bastion и сетью клиента работает
- [ ] `node_exporter` / `windows_exporter` установлен на всех серверах
- [ ] `restic` бэкап выполнен первый раз, проверен (restore тестового файла)
- [ ] `prometheus.yml` обновлён, targets "up"

### День 3. Калибровка
- [ ] Пороги алертов настроены под реальный профиль нагрузки
- [ ] Grafana dashboard-ы расшарены клиенту (view-only)
- [ ] Первый weekly-report сгенерирован и отправлен

**DoD:** Alertmanager отправляет алерты в корректный чат; клиент подтвердил, что видит dashboard.

## 3. Реакция на P1-инцидент

**Определение P1:** остановлен бизнес-критичный сервис (1С, почта, телефония, БД).

| Тариф | SLA reaction | SLA resolution target |
|---|---|---|
| Bronze | ≤ 4 ч | ≤ 8 ч (раб.) |
| Silver | ≤ 2 ч | ≤ 4 ч |
| Gold | ≤ 1 ч, 24/7 | ≤ 4 ч, 24/7 |

**Регламент:**
1. Alertmanager → Telegram-чат `#incidents`.
2. Acknowledge в `/ack` в течение SLA-времени.
3. Создание инцидента в osTicket (Gold) / Notion (Bronze/Silver).
4. Диагностика: Grafana → Loki (Silver+) → Wazuh (Gold).
5. Уведомить клиента в его чат: «Зафиксировали X, работаем, обновление через 30 мин».
6. Резолюция → уведомление клиенту → пост-мортем (Gold, обязательно) или краткий разбор (остальные).

**DoD:** Инцидент закрыт, клиент подтвердил, что сервис работает, пост-мортем опубликован в Notion.

## 4. Проверка бэкапов (еженедельно)

**Когда:** каждую пятницу, 14:00.

**Скрипт (полуавтомат):**
```bash
for client in /opt/mspshield/clients/*.yml; do
  bash /opt/mspshield/scripts/verify_restic.sh "$client"
done
```

**Что делает скрипт:**
1. `restic check --read-data-subset=5%` — проверка целостности 5% архива
2. Восстановление случайного файла во `/tmp/restic-verify/`
3. Сравнение md5 с продовой версией
4. Запись результата в таблицу `clients_backup_status`

**Алерт:** если восстановление не удалось — P1.

## 5. Еженедельный отчёт клиенту

**Когда:** понедельник, 10:00.

**Содержание:**
- Uptime по каждому серверу (%)
- Кол-во алертов за неделю (P1/P2/P3)
- Проведённые работы (ссылка на tickets)
- Статус бэкапов (все OK / были проблемы)
- План на ближайшую неделю

**Формат:** PDF + ссылка в Grafana (view-only).

**DoD:** Отчёт отправлен до 10:30 в Telegram + email.

## 6. Расторжение договора

**Триггер:** клиент прислал уведомление (минимум за 30 дней).

**Шаги:**
1. Зафиксировать дату прекращения в календаре.
2. За 14 дней — передать клиенту:
   - Экспорт конфигурации из Git (тарболл + git bundle)
   - Все ключи WireGuard / SSH
   - Последние 3 бэкапа restic + пароль шифрования
   - Доступы к Grafana / Prometheus (перенос или снимок)
3. За 7 дней — совместный звонок: вопросы по передаче.
4. В день прекращения — отключить мониторинг, удалить клиента из prometheus.yml.
5. Через 30 дней — удалить все данные клиента с наших серверов (подтвердить клиенту).

**DoD:** Клиент подписал акт о передаче материалов. Все его данные удалены.
