# 2. Как спокойно разобраться в незнакомом сервере

После сбоя документация может говорить одно, а сервер — другое. В такой ситуации опасно сразу перезапускать контейнеры или менять настройки. Сначала нужно понять, что действительно запущено.

## Начинаем с версии проекта

```bash
git rev-parse HEAD
```

Команда показывает номер текущего коммита. Коммит — это сохранённая версия файлов в Git. Команда ничего не изменяет.

Скопируйте полученный номер и найдите его в GitHub. Так можно понять, совпадает ли сервер с основной веткой проекта.

Теперь проверьте незаписанные изменения:

```bash
git status --short
```

Пустой ответ означает, что Git не видит изменённых файлов. Если появились строки, не удаляйте их. Сначала выполните `git diff` и сохраните результат в журнале работ.

## Смотрим, какие сервисы описаны в Compose

```bash
docker compose config --services
```

Docker Compose читает файл `docker-compose.yml`, подставляет переменные и выводит имена сервисов. Контейнеры эта команда не запускает.

После этого посмотрите фактическое состояние:

```bash
docker compose ps
```

Здесь важны три вещи: запущен ли контейнер, какой у него статус и какие порты опубликованы на сервере.

`Up` означает только то, что процесс контейнера работает. Это ещё не доказывает, что сайт принимает заявки или что MAX доставляет сообщения.

## Проверяем открытые порты

```bash
sudo ss -lntp
```

Команда показывает программы, которые ждут сетевые подключения.

В MSPShield backend должен быть доступен на `127.0.0.1:8001`. Адрес `127.0.0.1` означает, что подключиться можно только с самой виртуальной машины. Если вы увидели `0.0.0.0:8001`, порт открыт на всех сетевых интерфейсах. Для production это ошибка.

## Проверяем ответ backend

```bash
curl -fsS http://127.0.0.1:8001/api/health
```

`curl` отправляет HTTP-запрос. Адрес указывает на backend на этой же машине.

Параметр `-f` заставляет команду завершиться ошибкой при ответе 400 или 500. `-sS` убирает индикатор загрузки, но оставляет текст ошибки.

Успешный ответ подтверждает только работу этого адреса. Он не гарантирует, что база данных, Kaiten, почта и MAX доступны.

## Смотрим журнал конкретного сервиса

```bash
docker compose logs --tail 100 backend
```

Команда показывает последние сто строк журнала backend. Она ничего не перезапускает.

Сначала найдите время ошибки. Затем прочитайте несколько строк до неё и после неё. Одна строка без контекста часто приводит к неверному выводу.

## Пример расследования

Допустим, сайт открывается, но новая заявка не появляется в Kaiten.

Не начинайте с перезапуска всего проекта. Проверьте путь заявки по частям:

1. Откройте инструменты разработчика браузера и посмотрите ответ запроса `/api`.
2. Проверьте журнал backend за то же время.
3. Убедитесь, что запись появилась в MongoDB.
4. Проверьте очередь отправки в Kaiten.
5. Только после этого проверяйте ключ Kaiten и доступность его API.

Если запись есть в базе, но нет в Kaiten, сайт и сохранение работают. Неисправность находится дальше по цепочке.

## Практика

На учебной VM запишите:

- номер коммита;
- список сервисов Compose;
- состояние контейнеров;
- порт backend;
- ответ `/api/health`;
- последние десять строк журнала backend.

Рядом с каждым пунктом напишите простыми словами, что именно он подтверждает и чего не подтверждает.
