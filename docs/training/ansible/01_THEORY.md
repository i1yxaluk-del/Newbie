# 1. Как работает Ansible

[← Курс](README.md) · [Практика](02_PRACTICE.md)

## От ручной команды к описанию состояния

Ручная команда «дописать строку в файл» при каждом повторе может добавлять дубликат. Задача Ansible «файл должен иметь такое содержимое и права» сначала сравнивает состояние, затем меняет только необходимое. Это называется **идемпотентностью**: повтор при неизменных входных данных не должен создавать новые изменения. Это свойство модуля и конкретного сценария, а не волшебная гарантия Ansible.

```text
Управляющий узел
  → ansible.cfg: общие настройки подключения
  → inventory: какие узлы и группы существуют
  → playbook: к какой группе применить какие задачи
  → переменные + шаблон → модуль на управляемом узле
  → результат задачи → обработчик изменения → проверка сервиса
```

**Список узлов** (`inventory`) — адресная книга. **Сценарий** (`playbook`) — перечень этапов для выбранных групп. **Роль** — повторно используемый набор задач, шаблонов и значений по умолчанию. **Модуль** — программа конкретного действия (`copy`, `file`, `template`, `service`). **Обработчик** (`handler`) обычно вызывается через `notify`, когда задача сообщает об изменении; по умолчанию выполняется ближе к концу этапа, не обязательно сразу.

## Где исполняется код

Команда `ansible-playbook` запускается на управляющем узле. Обычно модуль исполняется по SSH на целевом узле; `lookup()` читает данные на управляющем узле. Поэтому `lookup('env', ...)` не означает окружение клиента. Шаблон берётся с управляющего узла, итоговый файл создаётся на целевом. `connection: local` в учебном примере явно оставляет выполнение на машине ученика.

`become: true` повышает права на целевой машине (обычно через sudo). Оно не выдаёт разрешение владельца и не делает операцию безопасной. Ошибочный `hosts: all` с повышением прав затронет весь выбранный перечень.

## Переменные и приоритет

Пример: в `defaults/main.yml` роли задано стандартное время backup. В `group_vars` — расписание клиента. Для конкретного узла его может уточнить `host_vars`; `-e` обычно имеет более высокий приоритет. Это не полная таблица всех видов переменных Ansible: для спорного случая проверить официальную документацию и фактические входы.

Читая `{{ restic_schedule }}`, найдите не только первое упоминание, но и место переопределения. Без этого невозможно понять, какой файл получится. Не выводите все переменные команды `debug` или полный результат `ansible-inventory --list`, если среди них есть секреты.

**Ansible Vault** шифрует секретный файл в репозитории. Во время выполнения секрет расшифрован в памяти; его всё ещё можно раскрыть журналом, `--diff`, временным файлом или командной строкой. `no_log: true` скрывает результат конкретной задачи, но не исправляет незащищённое хранение и не очищает чужие журналы.

## Как понимать результат

| Результат | Значение | Что проверить |
|---|---|---|
| `ok` | Задача завершена без заявленного изменения | Не является проверкой всего приложения |
| `changed` | Модуль сообщил об изменении | Было ли оно ожидаемо; нужен ли обработчик |
| `skipped` | Условие исключило задачу | Не перепутаны ли ОС, группа или переменная |
| `unreachable` | Узел недоступен для Ansible | Адрес, маршрут, SSH, ключ узла, учётная запись |
| `failed` | Действие/проверка завершились ошибкой | Остановить расширение на другие узлы, изучить причину |

`--syntax-check` проверяет структуру сценария, но не существование пакета или работоспособность сети. `--check` прогнозирует изменения там, где модуль это умеет: часть задач пропускается, а некоторые явно могут выполняться даже в этом режиме. `--diff` показывает различия и способен раскрыть пароли. «Предварительная проверка прошла» не равна проверенному откату.

## Порядок зависимостей

Для сервиса нужны пользователь/каталоги → программа → конфигурация → проверка синтаксиса → запуск → прикладная проверка. Для backup: доступ к хранилищу и ключ → подготовленный репозиторий → чтение источников → расписание → успешный запуск → восстановление. Таймер, включённый раньше подготовки репозитория, может успеть запустить неготовую задачу.

`serial: 1` ограничивает одновременную обработку узлов, но не выбирает одного клиента. `--limit` сужает перечень, а `--tags` выбирает задачи. Нужны обе проверки: **где** и **что** будет выполнено.
